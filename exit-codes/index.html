Exit codes: 0 to 255 and Docker conventions

Codes 0-124 are application-defined. 125 is Docker's own start-failure code, 126, 127 and 128 have shell or Docker meanings, 129-192 are signal terminations (128 + signal 1-64), and 255 covers SSH fatal errors and exit -1. Select the exact code to see proof commands and fixes.

The 128 + n rule, and where it stops applying

A process terminated by a fatal signal is reported by its parent shell as 128 + signal number. This is a shell convention, not a kernel exit status: the kernel records a wait status, and the shell maps the terminating signal into that 128+n range.

  • 129 = 128 + 1 — SIGHUP, terminal hangup or a reload that had no handler.
  • 130 = 128 + 2 — SIGINT, usually Ctrl+C in an interactive session.
  • 137 = 128 + 9 — SIGKILL, the cgroup OOM killer, a failed liveness probe after the grace period, or an explicit kill -9.
  • 139 = 128 + 11 — SIGSEGV, a native memory fault, not an out-of-memory kill.
  • 143 = 128 + 15 — SIGTERM, the default graceful stop request for Docker, Kubernetes and systemd.

The rule does not make 125, 126, 127 or 255 signal codes. Those come from Docker, the shell or SSH and have their own meanings. If a status is not in the 129-192 range and the process was not killed, treat it as an application or runtime status and read the sender's documentation rather than the signal table.

The defensible workflow is always the same: read the runtime's recorded status, confirm whether a signal was involved, identify the sender, then change the configuration that caused it. Guessing from the number alone is how a memory limit gets raised when the actual cause was a shell that never forwarded SIGTERM.

Frequently asked questions

How do I tell an OOM kill from a normal shutdown?

Exit 137 is SIGKILL, but the sender matters. Run docker inspect <id> --format '{{.State.OOMKilled}}' or read the Kubernetes lastState reason. OOMKilled true means the cgroup memory limit was exceeded; reason Error with a failed liveness probe means the kubelet escalated after the grace period. Exit 143 is the SIGTERM stop request, not an OOM kill.

Why is the exit code 128 + n?

Shells encode a signal termination as 128 plus the signal number so it cannot be confused with a normal 0-127 application status. SIGKILL is 9, so 137; SIGTERM is 15, so 143. The kernel's wait status is different, but the shell and most container tools present the 128+n value.

Does Kubernetes use Docker exit codes?

Kubernetes records the container process status and reason in .status.containerStatuses[].lastState.terminated. The numeric meanings match the process and signal conventions described here, but start failures are reported as pod events such as FailedScheduling, ErrImagePull or FailedMount rather than as exit 125.

What should I check first when a container restarts?

Get the last exit code, the reason and whether OOMKilled is true, then read the previous container logs. Those three facts separate a signal kill from an application failure and from a runtime start failure. Change the configuration that matches the evidence instead of raising memory or restart counts blindly.
